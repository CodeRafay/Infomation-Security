### **1. HTTP Sessions & Cookies**

#### **The Problem: Stateless Nature of the Web**

- **Concept:** HTTP is a stateless protocol. This means the server does not keep a record of the user between requests .

- **The Issue:** When a user sends a second request, the server cannot recognize if it is the same user who visited before .

- **Solution:** We need a mechanism to maintain "state" (memory) of the user's interaction, which is achieved through Cookies and Sessions.

#### **Cookies (Client-Side State)**

- **Definition:** Cookies are small pieces of data designed to keep track of the user at the **user's end** (browser).

- **Mechanism:**

1. **First Request:** User sends a request. The server processes it and sends a response including a `Set-Cookie` header.

2. **Storage:** The browser saves these cookies.

3. **Subsequent Requests:** When the user visits again, the browser automatically attaches the relevant cookies in the HTTP request header.

4. **Recognition:** The server reads the cookie to identify the user.

- **Types of Cookies:**
- **Session Cookies:** Temporary cookies used to store a Session ID .

- **Tracking/Third-Party Cookies:** Used by advertisement networks (like Google or Facebook) to track user behavior across different sites (Site A, B, and C) for targeted ads.

- _Mitigation:_ Use anonymous browsing or block third-party cookies .

#### **Sessions (Server-Side State)**

- **The Limitation of Cookies:** You cannot trust data stored solely on the client side (cookies).
- _Example:_ A shopping site storing a bill amount ($1000) in a cookie. A malicious user could simply edit the cookie file to change the price to $1 .

- **The Solution (Sessions):** Critical data (like prices, privileges) must be saved on the **Server**.

- **Session ID:**
- To link the user to their data on the server, a **Session ID** is used.

- The Session ID is a unique random number assigned to the user upon login.

- **Rule:** "Have the session ID = Have the access".

- **Storage:** The Session ID is stored in a cookie on the browser, while the actual data corresponds to that ID in the server's database/memory.

### **2. Cookie Theft**

Cookie theft is the act of an attacker stealing the session token (cookie) to impersonate a user.

- **Sniffing Attacks:**
- If the connection is not secure (HTTP instead of HTTPS), an attacker on the same network can "sniff" or intercept the traffic.
- Since cookies are attached to HTTP requests , the attacker can read the plaintext Session ID and use it to log in.

- **Cross-Site Scripting (XSS) (Additional Knowledge):**
- If a website is vulnerable to XSS, an attacker can inject JavaScript that executes in the victim's browser.
- _Malicious Script:_ `var stolenCookie = document.cookie;`
- The script then sends this cookie to the attacker's server.

- **Man-in-the-Middle (MITM) (Additional Knowledge):**
- Even with HTTPS, if an attacker can downgrade the connection (SSL Stripping) or trick the user into accepting a fake certificate, they can decrypt the traffic and steal cookies.

### **3. Session Hijacking & Mitigation**

#### **Session Hijacking (Side-Jacking)**

- **Definition:** A form of identity theft where an attacker takes over a user's Web session by obtaining their Session ID.

- **Mechanism:** Once the attacker has the Session ID (via theft), they inject it into their own browser. The server sees the valid ID and grants the attacker access to the user's account without needing the username or password.

#### **Common Hijacking Methods (Additional Knowledge)**

1. **Session Sniffing:** Intercepting unencrypted network traffic.
2. **Session Fixation:** The attacker forces the victim's browser to use a known Session ID _before_ the victim logs in. Once they log in, the attacker (who already knows the ID) gains access.
3. **Cross-Site Scripting (XSS):** Using scripts to steal the `document.cookie`.

#### **Mitigation Strategies (Defense)**

**1. Secure Transmission (Network Level)**

- **HTTPS (SSL/TLS):** Encrypts all traffic between client and server. Even if an attacker sniffs the packet, they cannot read the Session ID.
- **Secure Flag:** When setting a cookie, the server should set the `Secure` flag. This tells the browser: "Only send this cookie over encrypted (HTTPS) connections."
- _Example:_ `Set-Cookie: session_id=xyz; Secure;`

**2. Protecting Against XSS (Application Level)**

- **HttpOnly Flag:** This is a critical defense.
- When setting a cookie, the server sets the `HttpOnly` flag.
- _Effect:_ The browser prevents client-side scripts (JavaScript) from accessing the cookie. `document.cookie` will return an empty string for that specific cookie, preventing XSS theft.
- _Example:_ `Set-Cookie: session_id=xyz; HttpOnly;`

**3. Session Management Best Practices (Server Level)**

- **Session Rotation:** The server should issue a **new** Session ID immediately after a successful login. This mitigates Session Fixation attacks.
- **Session Timeout:** Implement short idle timeouts (e.g., log out after 10 mins of inactivity) and absolute timeouts (force re-login after 24 hours).
- **SameSite Attribute:**
- `SameSite=Strict` or `SameSite=Lax`.
- Prevents the browser from sending the cookie if the request originated from a different website (mitigates Cross-Site Request Forgery - CSRF).

**4. User Behavior Profiling (Advanced)**

- Bind the session to the user's IP address or User-Agent string. If a request comes with the correct Session ID but a different IP/Browser, invalidate the session (Note: IP binding can be tricky with mobile users switching networks).
