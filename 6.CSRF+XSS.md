### **1. Cross-Site Request Forgery (CSRF)**

#### **Concept & Definition**

- **Definition:** CSRF is a web security vulnerability that tricks a victim into performing actions they do not intend to perform.

- **Mechanism:** It forces the victim's browser to send a forged HTTP request, including the victim's session cookie and authentication information, to a vulnerable web application.

- **Goal:** The attacker aims to cause state-changing actions, such as:
- Changing the email address on an account.

- Changing a password.

- Transferring funds.

#### **How CSRF Works (The Scenario)**

- **The Setup:**

1. **Target Website:** A user is logged into a legitimate site (e.g., `www.facebook.com`) and has an active session (Session ID).

2. **Malicious Website:** The user visits a different website (e.g., `www.web.com`) hosted by the attacker.

- **The Attack Execution:**
- The malicious page (`web.com`) contains a hidden form or script that targets `facebook.com`.
- As the user loads the malicious page, it automatically sends a request to the Facebook server (e.g., a "Delete Account" request).

- **The Vulnerability:** Since the user is already logged in, their browser automatically attaches the valid Facebook cookies/Session ID to this cross-site request. The Facebook server receives the valid cookies, assumes the user intended to make the request, and executes it.

#### **Countermeasures for CSRF**

**A. Referer Header (Unreliable)**

- **Concept:** The server checks the `Referer` HTTP header to see where the request originated. If it comes from an external domain (like `web.com`), the server blocks it.

  **Weakness:**

- Many users block the `Referer` header using proxies or browser settings for privacy reasons.

- Attackers can sometimes spoof or strip this header.
- **Verdict:** Not a reliable solution.

**B. Secret Token (Anti-CSRF Token)**

- **Concept:** The server attaches a unique, unpredictable secret string (token) to each protected web page.

  **Mechanism:**

- When a legitimate form is loaded, the token is included as a hidden field.
- When the form is submitted, the server checks if the submitted token matches the one associated with the user's session.

- **Security:** Since the token is hidden in the page source and the attacker cannot read data from the target domain (due to SOP), the attacker cannot forge a request containing the correct token.

- **Dynamic Generation:** Developers can generate these tokens dynamically inside the page.

**C. Same-Site Cookies**

- **Concept:** A newer attribute for cookies that lets servers declare whether their cookies should be sent with cross-site requests.

  **Types:**

- **Strict:** The cookie is _never_ sent with cross-site requests. It effectively stops CSRF but can affect user experience (e.g., clicking a Facebook link from an email won't log you in automatically).

- **Lax:** The cookie is not sent on cross-site subrequests (like images or frames) but is sent when the user navigates to the origin site (e.g., following a link). This is the default in modern browsers.

### **2. Same-Origin Policy (SOP)**

#### **Definition**

- **The Golden Rule of Web Security:** SOP is a security mechanism enforced by web browsers that prevents scripts running on one origin from accessing data on a different origin.
- **Definition of an "Origin":** Two URLs have the same origin if they share the exact same:

1. **Protocol** (e.g., `http` vs `https`)
2. **Host** (e.g., `www.example.com`)
3. **Port** (e.g., `80`, `443`, `8080`)

#### **How it Works**

- **Restriction:** If a script on `http://attacker.com` tries to read the content of `http://bank.com/account`, the browser blocks access because the origins differ.
- **Scope:** SOP primarily restricts **read** access. It typically allows:
- **Writes:** Submitting a form to a different origin (which is why CSRF is possible).
- **Embedding:** displaying images, scripts, or iframes from different origins.

#### **Exceptions & Relaxations**

- **CORS (Cross-Origin Resource Sharing):** A mechanism where a server explicitly allows some cross-origin requests by sending specific HTTP headers (e.g., `Access-Control-Allow-Origin: *`).
- **HTML Tags:** Tags like `<script src="...">`, `<img src="...">`, and `<link href="...">` are allowed to load resources from other origins (but the script cannot read the raw content of those resources, only execute/display them).

### **3. Cross-Site Scripting (XSS)**

#### **Concept & Definition**

- **Definition:** XSS is a vulnerability where an attacker injects malicious client-side scripts (usually JavaScript) into web pages viewed by other users.

- **Mechanism:** The malicious script executes within the victim's browser, allowing the attacker to steal cookies, session tokens, or manipulate the page content.

#### **Real-World Examples (From File)**

- **Samy Worm (MySpace, 2005):**
- Samy Kamkar created a worm on MySpace using XSS.
- **Payload:** When victims viewed Samy's profile, the script executed two actions:

1. Added Samy as a friend.

2. Updated the victim's profile to say "Samy is my hero".

- **Impact:** It infected over 1 million users in just 20 hours.

- **VoteHillary.org (2008):**
- During the US election, Hillary Clinton's campaign site was victim to XSS.
- Attackers injected code that changed the website's content to display information about Barack Obama, while the URL remained `votehillary.org`.

#### **Comparison: XSS vs. CSRF**

| Feature         | Cross-Site Scripting (XSS)                                         | Cross-Site Request Forgery (CSRF)                                   |
| --------------- | ------------------------------------------------------------------ | ------------------------------------------------------------------- |
| **Full Name**   | Cross-Site Scripting                                               | Cross-Site Request Forgery                                          |
| **Mechanism**   | Injecting malicious script to execute in victim's browser          | Forcing victim's browser to send unintended requests                |
| **Requirement** | **JavaScript is required** to perform this attack                  | JavaScript is **not required** (can be done with HTML forms/images) |
| **Trust Model** | Exploits the user's trust in a website (The site accepts bad code) | Exploits the website's trust in the user's browser                  |
| **Severity**    | Generally more harmful; attacker can do anything the user can do   | Limited to actions the application exposes (e.g., buy, delete)      |
| **Protection**  | Protected sites can still be vulnerable to CSRF                    | CSRF protection does not stop XSS                                   |

#### **Countermeasures for XSS**

**A. Content Security Policy (CSP)**

- **Definition:** An HTTP header that allows site operators to restrict the resources (such as JavaScript, CSS, Images) that the browser is allowed to load for that page.

- **Function:** It prevents XSS by disabling the execution of inline scripts and only allowing scripts from trusted domains (whitelisting).

**B. Input Validation & Output Encoding (Additional Knowledge)**

- **Input Validation:** Ensure that input meets expected formats (e.g., ensure age is only a number).
- **Output Encoding:** Convert special characters into their HTML entity equivalents before rendering them in the browser.
- _Example:_ Convert `<script>` to `&lt;script&gt;`. This ensures the browser treats the input as text content rather than executable code.

#### **Writing a Self-Propagating XSS Worm (Concept)**

- The slides mention the concept of a "Self-Propagating XSS Worm".

- **How it works:**

1. **Infection:** User views an infected profile/page.
2. **Execution:** The XSS payload executes.
3. **Propagation:** The payload uses the user's session to inject _itself_ into the user's own profile/pages.
4. **Result:** Anyone who views the newly infected profile also gets infected, causing exponential growth (like the Samy Worm).
