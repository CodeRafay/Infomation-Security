### **1. Database Security Overview**

- **Definition:** Database security refers to the collective measures used to protect and secure a database or database management system (DBMS) from illegitimate use and malicious cyber threats.

- **Core Concepts (Additional Knowledge):**
- **Data at Rest Encryption:** Encrypting the actual database files on the disk so that if the physical server is stolen, the data remains unreadable.
- **Data in Transit Encryption:** Using SSL/TLS to encrypt the connection between the application and the database to prevent sniffing.
- **Access Control:** Implementing strict authentication (who are you?) and authorization (what can you do?) policies.
- **Auditing:** Keeping detailed logs of who accessed what data and when to track suspicious behavior.

### **2. SQL Injection (SQLi) Attack**

#### **Concept & Definition**

- **What is SQL Injection?** SQL Injection is a code injection technique where an attacker executes malicious SQL statements (also known as a payload) that control a web application's database server.

- **The Mechanism:**
- It occurs when an application takes user input (data) and concatenates it directly into a database query string (code) without validation.

- This effectively "turns data into code," allowing the attacker to alter the query's logic.

- **Analogy:** It is similar to other injection attacks like **System Injection** (executing OS commands) or **Cross-Site Scripting (Javascript Injection)**, where the core failure is trusting user input.

#### **Vulnerability Scenario (From Slides)**

- **Web Application Architecture:** A typical vulnerable setup involves a user interface (browser), a web server (e.g., Apache/PHP), and a database (e.g., MySQL) running in containers (Docker).

- **The Flaw:**
- The application uses a **SELECT statement** to fetch records based on user input (e.g., searching for a name or ID).

- **Vulnerable Code Logic:** `SELECT * FROM users WHERE name = '` + `userInput` + `'`.

#### **Attack Execution Examples**

- **1. Authentication Bypass (The "1=1" Attack):**
- _Goal:_ Log in without knowing the password or view all records.
- _Injection:_ The attacker inputs `' OR '1'='1`.
- _Resulting Query:_ `SELECT * FROM users WHERE name = '' OR '1'='1'`.
- _Why it works:_ Since `'1'='1'` is always **TRUE**, the database returns all rows in the table, effectively bypassing the specific name check.

- _Comment Syntax:_ Attackers often use `#` (MySQL) or `--` (SQL standard) to comment out the rest of the original query (like the password check).

- **2. Modifying the Database (Update/Delete):**
- _Goal:_ Alter data or destroy the database.
- _Injection:_ `'; UPDATE users SET password='hacked' WHERE user='admin'; #`
- _Limitation:_ In many PHP configurations (e.g., using `mysqli_query`), the API usually supports only **one single SQL statement** per call. This prevents "stacking" queries (running a SELECT followed by a DELETE in one go), acting as a partial accidental countermeasure.

#### **Types of SQL Injection (Additional Knowledge)**

- **In-band SQLi (Classic):** The attacker uses the same communication channel to launch the attack and gather results (e.g., seeing the data on the webpage).
- _Union-based:_ Using the `UNION` operator to combine the results of the original query with the results of a malicious injected query.

- **Inferential SQLi (Blind):** The attacker sends data payloads and observes the server's response behavior (true/false) rather than seeing the actual data.
- _Time-based:_ Sending a command to make the database "sleep" (e.g., `SLEEP(10)`). If the page takes 10 seconds to load, the injection was successful.

### **3. SQL Injection & Countermeasures**

Defense relies on distinguishing between **what is code** and **what is data**.

#### **A. Ineffective Countermeasures (What NOT to do)**

- **Blacklisting/Filtering:** Trying to manually remove "bad characters" (like `'`, `#`, `OR`).
- _Why it fails:_ Attackers can easily bypass filters using encoding (Hex, URL encoding) or alternative SQL syntax.

- **String Replacement:** Writing code to replace keywords like "SELECT" or "DROP" is unreliable and prone to error.

#### **B. Primary Defense: Prepared Statements (The Solution)**

- **Concept:** The most reliable solution is to **Separate Code and Data**.

- **How it Works:**

1.  **Prepare:** The application sends the SQL query structure to the database _first_, using placeholders (e.g., `?` or `:id`) instead of the actual data.

2.  **Compile:** The database parses, compiles, and optimizes the query plan.
3.  **Execute:** The application sends the user input (data) separately.

- **Why it Secure:** The database treats the input strictly as **data**, never as **executable code**. Even if the input is `' OR '1'='1`, the database looks for a user whose literal name is specifically that string, rather than executing the logic.

- **Implementation Example (PHP):**
- Use `$conn->prepare("SELECT * FROM users WHERE id = ?")`.
- Then `bind_param` to attach the user input to the `?`.

#### **C. Secondary Defenses (Additional Knowledge)**

- **Input Validation (White Listing):** Ensure input matches a strict expected pattern (e.g., if a UserID is expected, ensure the input is strictly an **Integer**).
- **Least Privilege Principle:** The database account used by the web application should only have the permissions necessary for its function.
- _Example:_ A login page's database connection should only have `SELECT` permissions, not `DROP` or `DELETE`.

- **Web Application Firewall (WAF):** A security appliance that sits in front of the web server and inspects incoming traffic for common attack patterns (like SQL injection strings) to block them before they reach the application.
